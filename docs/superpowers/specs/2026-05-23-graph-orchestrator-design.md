# Design: Graph-Based Agent Orchestration

Generated by /superpowers:brainstorming on 2026-05-23
Branch: main
Repo: ad_creative/hermes_agent_go
Status: APPROVED

## Problem Statement

hermes_agent_go's core agent loop (`conversationLoop()`) is a 200+ line monolithic method that couples LLM invocation, tool execution, parallel dispatch, context compression, budget tracking, and event distribution into a single function. Adding new agent behaviors (streaming-only mode, human-in-the-loop, custom routing) requires modifying this method directly. As an internal platform serving multiple teams, hermes needs a composable orchestration layer where agent workflows can be defined, customized, and extended without touching core loop code.

## Design: Graph-Based Orchestration

Replace the monolithic `conversationLoop()` with a graph executor model inspired by AWS Step Functions / oe_flow. The agent loop becomes a directed graph of typed nodes (LLM, Tool, Choice, Parallel, End) connected by edges. A lightweight executor walks the graph, delegating actual work to hermes's existing model and tool layers through narrow adapter interfaces.

All orchestration primitives live in a new `pkg/orchestrator/` package with zero external dependencies.

### Core Interfaces

```go
// NodeRunner — every node type implements this
type NodeRunner interface {
    Run(ctx context.Context, node *NodeSpec, input interface{},
        execCtx *ExecutionContext) (*NodeResult, error)
}

// LLMInvoker — hermes model.Router adapts to this
type LLMInvoker interface {
    Chat(ctx context.Context, model string, messages []LLMMessage,
        tools []string, cfg LLMConfig) (*NodeResult, error)
    ChatStream(ctx context.Context, model string, messages []LLMMessage,
        tools []string, cfg LLMConfig, onDelta func(string)) (*NodeResult, error)
}

// ToolInvoker — hermes tool.Registry adapts to this
type ToolInvoker interface {
    Invoke(ctx context.Context, resource string, input interface{},
        timeout uint) (*NodeResult, error)
}

// Tracer — observability hook, replaces single EventCallback
type Tracer interface {
    OnNodeStart(ctx context.Context, nodeID, nodeType string, input interface{})
    OnNodeEnd(ctx context.Context, nodeID, nodeType string, output *NodeResult, err error)
    OnStreamDelta(ctx context.Context, content string)
}

// MemoryStore — session persistence, SessionDB implements this
type MemoryStore interface {
    SaveSession(ctx context.Context, session *ConversationMemory) error
    LoadSession(ctx context.Context, sessionID string) (*ConversationMemory, error)
    DeleteSession(ctx context.Context, sessionID string) error
}
```

### Human-in-the-Loop

`ask_human` is a tool in the LLM's tool list, identical to `read_file` or `bash`. The LLM decides when human input is needed — there is no special routing logic.

**Flow:**

1. LLM returns `tool_calls: [ask_human(question, options)]`
2. Choice node routes to `dispatch_tools`
3. ParallelRunner spawns a branch for `ask_human`
4. ToolRunner → ToolInvoker.Invoke("builtin/ask_human", ...) detects this is a human tool
5. Returns `NodeResult{Status: "pending", Interrupt: true, Output: {question, options}}`
6. Executor detects `Interrupt: true`, saves an `ExecutionSnapshot`, returns control to the caller
7. Caller presents the question to the human, collects the response
8. Caller calls `executor.Resume(snapshot, humanResponse)`
9. The humanResponse becomes the return value of the `ask_human` tool call
10. Execution continues with LLM receiving the human's answer

**HumanRunner (pkg/orchestrator/runner/human.go):**

```go
type HumanConfig struct {
    Prompt  string      `json:"Prompt,omitempty"`
    Actions []string    `json:"Actions,omitempty"`
    Timeout uint        `json:"Timeout,omitempty"`
    Schema  interface{} `json:"Schema,omitempty"`
}

type HumanRunner struct{}

func (r *HumanRunner) Run(ctx context.Context, node *NodeSpec,
    input interface{}, execCtx *ExecutionContext) (*NodeResult, error) {
    return &NodeResult{
        Status:    "pending",
        Interrupt: true,
        Output:    input,
    }, nil
}
```

**ExecutionSnapshot (pkg/orchestrator/executor/snapshot.go):**

```go
type ExecutionSnapshot struct {
    ExecutionID string
    CurrentNode string
    Step        int
    WorkMem     *ExecutionContext
    ConvMem     *ConversationMemory
    GraphHash   string
    CreatedAt   time.Time
}
```

**Executor changes:**

```go
// Execute returns (output, snapshot, error).
// snapshot is nil on normal completion, non-nil when interrupted.
func (e *Executor) Execute(ctx context.Context, g *Graph,
    input interface{}) (interface{}, *ExecutionSnapshot, error)

// Resume continues execution from a saved snapshot.
func (e *Executor) Resume(ctx context.Context, g *Graph,
    snap *ExecutionSnapshot, humanResponse interface{}) (interface{},
    *ExecutionSnapshot, error)
```

**Agent.Run() signature change:**

```go
// Run returns (reply, pending, error).
// pending=true means execution paused at a human node, waiting for input.
// Call Resume(humanResponse) to continue.
func (a *AIAgent) Run(ctx context.Context, input string) (string, bool, error)
func (a *AIAgent) Resume(ctx context.Context, humanResponse interface{}) (string, bool, error)
```

**SnapshotStore (implemented by SessionDB):**

```go
type SnapshotStore interface {
    SaveSnapshot(ctx context.Context, sessionID string,
        snap *ExecutionSnapshot) error
    LoadSnapshot(ctx context.Context, sessionID string) (*ExecutionSnapshot, error)
    DeleteSnapshot(ctx context.Context, sessionID string) error
}
```

**Platform adapters for human input:**

| Platform | Pause behavior | Resume behavior |
|---|---|---|
| CLI | Print prompt, show stdin prompt | Read stdin line → Resume() |
| HTTP API | Return `200 {status:"pending", prompt:"...", session_id:"..."}` | `POST /resume {session_id, response}` → Resume() |
| Telegram/Discord | Send message + inline keyboard | Bot callback → Resume() |

**ask_human tool schema** (injected into LLM tool list):

```json

  "name": "ask_human",
  "description": "Pause and ask the user for input. Use when: (1) making a decision with multiple valid options, (2) user instructions are ambiguous, (3) a proposed action is destructive and needs confirmation, (4) you lack domain knowledge the user has. Do NOT use for trivial yes/no questions.",
  "parameters": {
    "type": "object",
    "properties": {
      "question": { "type": "string", "description": "The question to ask" },
      "options":  { "type": "array", "items": {"type": "string"}, "description": "Multiple choice options (optional)" },
      "context":  { "type": "string", "description": "Why this is needed now" }
    },
    "required": ["question"]
  }
}
```

**Design notes:**

- The LLM has agency — it decides when to ask, no pre-defined trigger rules
- A single Graph execution can have multiple human nodes (multi-step approval)
- Snapshots persist to SessionDB, so execution survives process restart
- Default Graph does NOT include `ask_human` in tools; users opt-in via config
- When not using HITL, `Execute()` returns `snapshot=nil` and behavior is unchanged

### Subsystem Mapping

| Subsystem | Before | After | Change |
|---|---|---|---|
| LLM invocation | conversationLoop calls router directly | LLMRunner → LLMInvoker → RouterAdapter | Add ~50 line adapter |
| Tool execution | conversationLoop calls registry directly | ToolRunner → ToolInvoker → RegistryAdapter | Add ~50 line adapter |
| Parallel tools | ParallelExecutor (hardcoded categories) | ParallelRunner (graph-driven) | Delete parallel.go |
| Condition routing | Hardcoded if/else | ChoiceRunner (JSON-defined) | Delete if/else chain |
| Iteration budget | IterationBudget (atomic counter) | Graph.MaxSteps | Delete budget.go |
| Context compression | maybeCompress() in loop | Choice branch → compress tool node | Keep compressor, change trigger |
| Event/observability | Single EventCallback func | Tracer interface (multi-subscriber capable) | Add interface, keep compat |
| Streaming | provider.ChatStream → callback | LLMInvoker.ChatStream → onDelta → Tracer | Add ChatStream to interface |
| Delegation | delegate_task tool | Same tool node, child agent uses simpler graph | Unchanged |
| TODO planning | System message injection | Inject into LLM SystemPrompt (like memory) | Unchanged |
| Memory | Bug: PrefetchAll twice, first result discarded, second uses "" query | PrefetchAll ONCE with real user input, injected into LLM config | Fix bug |
| Session persistence | SessionDB raw SQLite | ConversationMemory.MemoryStore ← SessionDB | Add interface |
| Human-in-the-Loop | Not supported | ask_human tool → Interrupt → Snapshot → Resume | New feature |

### Memory Bug Fix

Current code calls `PrefetchAll` twice:

1. `Run()` line 184: `PrefetchAll(ctx, userInput, sessionID)` → result discarded (`_ = memCtx`)
2. `conversationLoop()` line 253: `PrefetchAll(ctx, "", sessionID)` → actually injected, but query is empty string

In the new architecture, `PrefetchAll` is called once in `Run()`, with the real user input, and the result is injected into the LLM node's SystemPrompt before Graph execution. No second call, no empty query, no discarded result.

## Open Questions

- Config interpolation: `$model` / `$temperature` in Graph JSON need a config resolution pass. Define a `GraphConfigBinder` that maps `AgentConfig` fields to Graph placeholders.
- User Graph override: Allow users to provide custom Graph JSON via config file or env var (`HERMES_GRAPH`). Fall back to default graph if not provided.
- Node type extensibility: Should users be able to register custom `NodeRunner` types? If so, via init() or explicit registration API?

## Success Criteria

- `conversationLoop()` no longer exists; agent loop driven by `executor.Execute(graph)`
- Default agent behavior is identical to current (LLM → tools → loop → end)
- Memory prefetch called once, with correct user query, and actually injected
- Existing tools and model providers work without modification
- User can override default Graph via JSON
- All existing tests pass (or are updated to match new API)

## Dependencies

None external. All orchestration primitives are defined in `pkg/orchestrator/` using only Go standard library.
